Artificial Intelligence is everywhere. Companies are investing billions into AI-driven products, automation systems, predictive analytics and machine learning platforms. Yet surprisingly, most AI projects never reach production or fail to deliver business value.

The core truth: Building AI models is only a small part of the challenge. The real challenge lies in aligning technology with business objectives, data quality, operations and organisational readiness.
The AI Gold Rush

Organisations across industries race to adopt AI — banks use fraud detection, retailers use recommendation engines, healthcare firms predict diseases, logistics companies optimise delivery routes. Amazon, Netflix and Tesla have demonstrated enormous potential. But for every successful AI system, hundreds quietly fail behind the scenes.

Major Reason 1 — Poor Data Quality

Machine learning depends entirely on data. If the data is incomplete, duplicated, biased, inconsistent or outdated, even advanced algorithms fail. A model trained on poor data behaves like a student learning from incorrect textbooks.

Real-world example

A telecom company builds a customer churn model. Problems: missing customer records, incorrect billing information, duplicate customer IDs. The model makes inaccurate predictions and management loses trust. The project is cancelled — not because the algorithm failed, but because the data did.

# Detecting data quality issues programmatically

Major Reason 2 — No Clear Business Objective

Many organisations start AI projects because "everyone else is doing AI." That is dangerous. AI should solve measurable business problems — reduce fraud, improve customer retention, optimise supply chains, increase revenue. Without KPIs, AI becomes an expensive experiment.

Major Reason 3 — Models Never Reach Production

Building a model in a Jupyter notebook is easy. Deploying it reliably is difficult. This is where most companies struggle: APIs, cloud infrastructure, monitoring, scalability, MLOps.

The Hidden Problem: Organisational Readiness

Even technically strong AI systems fail when organisations resist change. Employees may distrust AI, fear automation, or avoid adoption. Successful AI transformation requires leadership support, employee training and process redesign.

Real-world failure: A retail company built a demand forecasting model with 92% prediction accuracy and a strong analytics pipeline — but managers ignored predictions and continued manual planning. The AI system failed despite strong engineering.

Building an ETL pipeline that runs once is easy. Building one that runs reliably every day for three years — handling upstream schema changes, late-arriving data and partial failures — is engineering. This article covers production-grade patterns using Apache Airflow 2.x and dbt Core.

DAG Design Principles

A Directed Acyclic Graph (DAG) in Airflow defines the workflow. The three rules every production DAG must follow: idempotency (re-running produces the same result), atomicity (each task either fully succeeds or fully fails), and observability (every step is measurable).

# airflow/dags/financial_etl.py
from airflow.decorators import dag, task
from airflow.providers.postgres.hooks.postgres import PostgresHook
from airflow.sensors.external_task import ExternalTaskSensor
from pendulum import datetime

@dag(
    schedule="0 6 * * MON-FRI",          # weekdays at 06:00 UTC
    start_date=datetime(2024, 1, 1),
    catchup=False,
    max_active_runs=1,
    default_args={"retries": 3, "retry_delay_seconds": 300},
)
def financial_etl_pipeline():

    wait_upstream = ExternalTaskSensor(
        task_id="wait_for_source_feed",
        external_dag_id="bloomberg_ingest",
        allowed_states=["success"],
        timeout=3600,
    )

    @task()
    def extract_holdings(**context) -> list:
        hook = PostgresHook(postgres_conn_id="source_db")
        rows = hook.get_records(
            "SELECT * FROM holdings WHERE updated_at >= %(run_date)s",
            parameters={"run_date": context["ds"]}
        )
        return rows

    @task()
    def run_dbt_models():
        import subprocess
        result = subprocess.run(
            ["dbt", "run", "--select", "tag:daily", "--target", "prod"],
            capture_output=True, text=True
        )
        if result.returncode != 0:
            raise RuntimeError(result.stderr)

    holdings = extract_holdings()
    wait_upstream >> holdings >> run_dbt_models()

financial_etl_pipeline()

Failure Recovery Patterns
The dead letter queue pattern: On extraction failure, write the failing batch to a dead-letter table with an error code and timestamp. A separate DAG retries dead-letter rows after upstream systems recover — preventing full pipeline re-runs.
Key Takeaways
  • Design every DAG task for idempotency — re-runs must be safe
  • Use ExternalTaskSensors instead of fixed time delays for upstream dependencies
  • dbt incremental models with unique_key prevent duplicate inserts on retries
  • Dead letter queues prevent cascading failures from poisoning entire pipeline runs
  • Tag dbt models by schedule frequency for granular Airflow orchestration

Power BI dashboards that take 30 seconds to load are not a visualisation problem — they are a data model problem. This article covers the performance patterns that take Power BI reports from sluggish to sub-second on datasets exceeding 100 million rows.

Measures vs Calculated Columns: The Critical Difference

Calculated columns are computed row-by-row at data refresh and stored in the model. Measures are computed on-the-fly at query time, only for the visible context. On large tables, calculated columns bloat the in-memory VertiPaq engine — always prefer measures.

-- ❌ WRONG: Calculated column (row-context, computed at refresh)
Revenue Category =
    IF( Sales[Revenue] > 10000, "High", "Low" )

-- ✅ RIGHT: Measure (filter-context, computed at query time)
Revenue Category Measure =
    IF(
        [Total Revenue] > 10000,
        "High", "Low"
    )

-- ❌ WRONG: SUMX iterating 50M rows unnecessarily
Slow Revenue = SUMX( Sales, Sales[Qty] * Sales[UnitPrice] )

-- ✅ RIGHT: Pre-compute Revenue at ETL layer, SUM in DAX
Fast Revenue = SUM( Sales[Revenue] )
Query Folding in Power Query

Query folding is Power Query's ability to translate M code back into a native SQL query executed on the source database — instead of pulling all rows into memory. Breaking the fold chain is a performance catastrophe on large tables.

// ✅ Query folds — SQL runs on the server
let
    Source = Sql.Database("server", "db"),
    tbl    = Source{[Schema="dbo",Item="Sales"]}[Data],
    filter = Table.SelectRows(tbl, each [Year] = 2024),  // folds
    cols   = Table.SelectColumns(filter, {"ID","Revenue"})  // folds
in cols

// ❌ Query BREAKS the fold — entire table loaded into RAM
let
    ...
    // Table.Buffer() always breaks folding
    buffered = Table.Buffer(tbl),
    filter   = Table.SelectRows(buffered, each [Year] = 2024)
in filter
Using Variables to Avoid Repeated Context Evaluation
-- ❌ SLOW: [Total Revenue] evaluated 3 times in different contexts
Variance % =
    DIVIDE( [Total Revenue] - [Budget], [Budget] )

-- ✅ FAST: VAR captures value once, reused
Variance % Optimised =
VAR vRevenue = [Total Revenue]
VAR vBudget  = [Budget]
VAR vDiff    = vRevenue - vBudget
RETURN
    IF( vBudget = 0, BLANK(), DIVIDE( vDiff, vBudget ) )
Key Takeaways
  • Never use calculated columns where a measure will do — they bloat VertiPaq memory
  • SUMX over millions of rows is an anti-pattern: pre-aggregate at ETL layer
  • Check query folding with View Native Query in Power Query Editor
  • Variables (VAR) prevent repeated filter-context evaluations in complex DAX
  • Use DAX Studio's Server Timings tab to profile query execution plans

Financial sentiment analysis goes beyond keyword matching — it requires understanding context, hedging language and domain-specific terminology. FinBERT, pre-trained on financial corpora, outperforms general BERT models by 12–18 percentage points on financial NLP benchmarks.

Why General BERT Fails on Financial Text
The word "volatile" is neutral in everyday language, but strongly negative in financial contexts. "Strong headwinds" sounds positive but signals difficulty. General language models consistently misclassify these domain-specific patterns.
FinBERT Pipeline
from transformers import AutoTokenizer, AutoModelForSequenceClassification
import torch, torch.nn.functional as F

# Load ProsusAI/finbert (pre-trained on 4.9B financial tokens)
tokenizer = AutoTokenizer.from_pretrained("ProsusAI/finbert")
model     = AutoModelForSequenceClassification.from_pretrained("ProsusAI/finbert")
model.eval()

def get_sentiment(text: str) -> dict:
    inputs = tokenizer(text, return_tensors="pt",
                       truncation=True, max_length=512)
    with torch.no_grad():
        logits = model(**inputs).logits
    probs  = F.softmax(logits, dim=-1)[0]
    labels = ["positive", "negative", "neutral"]
    return {l: round(p.item(), 4) for l, p in zip(labels, probs)}

# Example: Q3 earnings call excerpt
text = """We experienced strong headwinds in our EMEA division
           with margin compression of 340 basis points."""
print(get_sentiment(text))
# {'positive': 0.0312, 'negative': 0.9241, 'neutral': 0.0447}

Value-at-Risk (VaR) answers one question: "What is the maximum loss we should expect over a given period, at a given confidence level?" Monte Carlo simulation generates thousands of possible portfolio paths to answer this question robustly — without assuming normal return distributions.

The Problem with Parametric VaR
Historical parametric VaR assumes returns are normally distributed. Financial returns exhibit fat tails and negative skew — the 2008 crisis and COVID crash were 20σ+ events under normality assumptions. Monte Carlo handles non-normality naturally through historical return resampling.
Full Implementation
import numpy as np
import pandas as pd

# ── 1. Load historical returns ──────────────────────────────
prices  = pd.read_parquet("portfolio_prices.parquet")
returns = prices.pct_change().dropna()

weights = np.array([0.40, 0.30, 0.20, 0.10])  # AAPL,MSFT,BND,GLD
portfolio_value = 1_000_000                          # £1M portfolio

# ── 2. Cholesky decomposition preserves correlation ─────────
cov  = returns.cov()
L    = np.linalg.cholesky(cov.values())
mu   = returns.mean().values()

# ── 3. Monte Carlo simulation: 10,000 paths × 252 days ──────
N_SIMS, HORIZON = 10_000, 252
rng = np.random.default_rng(seed=42)

portfolio_returns = np.zeros(N_SIMS)
for i in range(N_SIMS):
    z   = rng.standard_normal((HORIZON, 4))
    sim = mu + (L @ z.T).T          # correlated returns
    portfolio_returns[i] = (sim @ weights).sum()

# ── 4. Compute VaR and CVaR ──────────────────────────────────
VaR_95  = np.percentile(portfolio_returns, 5)
VaR_99  = np.percentile(portfolio_returns, 1)
CVaR_95 = portfolio_returns[portfolio_returns <= VaR_95].mean()

print(f"1-Year VaR (95%):  £{VaR_95  * portfolio_value:,.0f}")
print(f"1-Year VaR (99%):  £{VaR_99  * portfolio_value:,.0f}")
print(f"CVaR (95%):        £{CVaR_95 * portfolio_value:,.0f}")

MetricValueInterpretation
VaR 95%-£82,4005% chance of losing more than £82K in a year

CVaR (Conditional VaR) is more informative than VaR for tail risk — it measures the expected loss in the worst cases, not just the threshold. Basel III requires banks to use CVaR (Expected Shortfall) over VaR for internal model capital calculations.
Key Takeaways
  • Use Cholesky decomposition to preserve inter-asset correlation in simulations
  • CVaR (Expected Shortfall) is a better tail risk measure than VaR for regulatory purposes
  • 10,000+ simulations are needed for stable 99% confidence interval estimates
  • Historical return resampling avoids normality assumptions that understate tail risk
  • Vectorise simulations with NumPy — pure Python loops are 100× slower

  • Silver MERGE operations use composite natural keys, not surrogate keys
  • Define data quality as YAML tests in dbt, not as ad-hoc SQL checks
  • Gold layer should be owned by analytics engineers, not data engineers
  • Schema evolution is handled by Delta Lake MERGE with schema evolution flags

The difference between a 0.71 AUC churn model and a 0.89 AUC churn model is rarely the algorithm — it is almost always the features. This article documents the feature engineering playbook used to lift a telecoms churn model from baseline to production-grade performance.

The Temporal Leakage Problem
The most dangerous bug in financial ML: Using future data to predict the past. If your "last 30-day spend" feature is computed from the full dataset rather than up to the prediction date, your model will appear to achieve near-perfect accuracy — then fail catastrophically in production.
import pandas as pd
import numpy as np

# ❌ LEAKY: computes rolling on full sorted df
df["spend_30d"] = df["spend"].rolling(30).sum()

# ✅ SAFE: point-in-time correct rolling features
def safe_rolling_features(df: pd.DataFrame, target_date: str) -> pd.DataFrame:
    """Only uses data available at target_date."""
    cutoff = pd.Timestamp(target_date)
    hist   = df[df["transaction_date"] < cutoff].copy()

    features = hist.groupby("customer_id").agg(
        spend_30d  = ("spend", lambda x: x.last("30D").sum()),
        spend_90d  = ("spend", lambda x: x.last("90D").sum()),
        tx_count   = ("tx_id", "count"),
        days_since = ("transaction_date", lambda x: (cutoff - x.max()).days)
    )
    return features
Rolling & Lag Feature Engineering
# Velocity features — rate of change signals
for col in ["spend", "login_count", "support_calls"]:
    df[f"{col}_30d"]    = df.groupby("customer_id")[col].transform(lambda x: x.rolling(30).sum())
    df[f"{col}_90d"]    = df.groupby("customer_id")[col].transform(lambda x: x.rolling(90).sum())
    df[f"{col}_trend"]  = df[f"{col}_30d"] / (df[f"{col}_90d"] / 3 + 1e-6)  # acceleration
    df[f"{col}_lag_1m"] = df.groupby("customer_id")[col].shift(30)

from fastapi import FastAPI, HTTPException
from pydantic import BaseModel
import joblib, numpy as np
from prometheus_client import Counter, Histogram, make_asgi_app

    spend_30d: float
    spend_trend: float
    days_since_last_tx: int
    support_calls_90d: int
    login_count_30d: int

async def predict(features: CustomerFeatures):

        X = np.array([[

Window functions are the single most powerful SQL feature for financial analytics — yet most analysts use only SUM() OVER (PARTITION BY). This article covers production query patterns for running totals, moving averages, YoY comparisons and cohort analysis used in live investment banking dashboards.

Running Portfolio Totals
-- Running AUM by portfolio, ordered by trade date
SELECT
    trade_date,
    portfolio_id,
    daily_pnl,
    SUM(daily_pnl) OVER (
        PARTITION BY portfolio_id
        ORDER BY     trade_date
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    )                              AS cumulative_pnl,
    SUM(market_value) OVER (
        PARTITION BY portfolio_id
        ORDER BY     trade_date
        ROWS BETWEEN 1 PRECEDING AND 1 FOLLOWING  -- 3-day centred window
    )                              AS smoothed_aum
FROM fct_portfolio_daily
30 / 90-Day Moving Average — Avoiding the NULL Trap
-- ROWS BETWEEN vs RANGE BETWEEN: critical difference
SELECT
    trade_date,
    close_price,
    -- ❌ RANGE: uses peer rows (duplicates inflate the avg)
    AVG(close_price) OVER (ORDER BY trade_date
        RANGE BETWEEN INTERVAL '29 days' PRECEDING AND CURRENT ROW) AS ma30_range,
    -- ✅ ROWS: always uses exactly 30 prior rows
    AVG(close_price) OVER (ORDER BY trade_date
        ROWS BETWEEN 29 PRECEDING AND CURRENT ROW) AS ma30_rows,
    -- NULL-safe: only compute when 30 full rows exist
    CASE WHEN COUNT(*) OVER (ORDER BY trade_date ROWS BETWEEN 29 PRECEDING AND CURRENT ROW) = 30
         THEN AVG(close_price) OVER (ORDER BY trade_date ROWS BETWEEN 29 PRECEDING AND CURRENT ROW)
         END                             AS ma30_safe
FROM market_prices
Year-over-Year with LAG
WITH monthly_revenue AS (
    SELECT
        DATE_TRUNC('month', trade_date)  AS month,
        SUM(commission_revenue)          AS revenue
    FROM  fct_trades
    GROUP BY 1
)
SELECT
    month,
    revenue,
    LAG(revenue, 12) OVER (ORDER BY month)   AS revenue_prior_year,
    ROUND(
        (revenue - LAG(revenue, 12) OVER (ORDER BY month))
        / NULLIF(LAG(revenue, 12) OVER (ORDER BY month), 0) * 100,
        2
    )                                             AS yoy_growth_pct
FROM monthly_revenue
ORDER BY month
Cohort Retention Analysis
WITH cohorts AS (
    SELECT
        customer_id,
        MIN(DATE_TRUNC('month', trade_date)) AS cohort_month
    FROM  fct_trades
    GROUP BY 1
),
activity AS (
    SELECT
        t.customer_id,
        c.cohort_month,
        DATE_TRUNC('month', t.trade_date) AS activity_month,
        DATEDIFF('month', c.cohort_month, DATE_TRUNC('month', t.trade_date)) AS period
    FROM  fct_trades t
    JOIN  cohorts c USING (customer_id)
)
SELECT
    cohort_month,
    period,
    COUNT(DISTINCT customer_id)     AS active_customers,
    FIRST_VALUE(COUNT(DISTINCT customer_id)) OVER (
        PARTITION BY cohort_month ORDER BY period
    )                                AS cohort_size,
    ROUND(COUNT(DISTINCT customer_id) * 100.0
          / FIRST_VALUE(COUNT(DISTINCT customer_id)) OVER (PARTITION BY cohort_month ORDER BY period), 1)
                                     AS retention_pct
FROM  activity
GROUP BY 1, 2
ORDER BY 1, 2
Key Takeaways
  • ROWS BETWEEN is almost always the right choice over RANGE BETWEEN for financial time series
  • Guard moving averages against early-period NULLs with a COUNT() OVER companion window
  • LAG(col, 12) for monthly YoY is cleaner and faster than a self-join on prior year
  • FIRST_VALUE() OVER (PARTITION BY cohort) eliminates the need for a separate cohort size subquery
  • NULLIF() in the denominator prevents divide-by-zero in growth rate calculations
